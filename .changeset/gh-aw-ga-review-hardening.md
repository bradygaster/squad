Hardened the Squad GH-AW (GitHub Agentic Workflows) source contract against nine confirmed GA-review findings:

- **`squad-improvement-gate.mjs`**: closed a test-coverage gap for rejecting a content-only modification of an already-tracked executable (`100755`) Markdown improvement target (the production `ALLOWED_FILE_MODE` guard was already correct; added realistic Git-mode regression/mutation tests).
- **`squad_approval_relay` contract**: made the `squad.md` → `squad-improvement-worker.md`/gate producer/receiver contract for the approval relay payload unambiguous as a JSON string end-to-end, preserving the distinct `squad_approval_relay` input name (gh-aw overwrites `aw_context`). Added compiled assertion/mutation coverage.
- **`squad-review-guard.mjs`**: confirmed and regression-tested that unauthorized/malformed override markers are rejected by authorized-admin-human filtering *before* cardinality/record parsing, so a malformed authorized record still fails closed and an unauthorized marker can never be counted.
- **`squad-planning-ontology.md`**: normalized the result-line template from `Result: ✅ PASS` to the exact `RESULT: PASS` string required by downstream parsers.
- **`squad-install-verifier.mjs`**: confirmed `verifyInstalledBytes()` normalizes only the one documented injected `source:` ownership-binding line before hashing, and fails closed on any other tamper; existing mutation-test table already covers this.
- **Numeric identity canonicalization**: numeric issue/comment IDs arriving via `issue_comment` are canonicalized to safe-integer strings before comparison against `workflow_dispatch` string inputs, with invalid forms rejected; covered by direct and relayed regression/mutation tests.
- **`squad-command-router.md`**: blocked replay of bot-authored standalone `/squad` issue/comment text while preserving trusted `workflow_dispatch` continuation and documented bot command behavior, covering both `created` and `edited` events.
- **`can_approve_pull_request_reviews`**: proved from gh-aw source that this is a single combined toggle gating both `GITHUB_TOKEN` PR creation *and* PR-review approval — it cannot be split via job-level `permissions:`. Per least-privilege policy (no weakened independent-human review gate), flipped to `false` across all public/enlistment/setup copies and added a fallback-to-issue mechanism (with a manual compare-URL link) to `squad-bootstrap.md` for when the push succeeds but the PR cannot be opened.
- **Mutable installation channel**: eliminated resolution of a mutable `commits/dev` ref for GA installs; setup now requires an explicit, pre-validated 40-character `SQUAD_SHA`, synchronized across public/enlistment docs and skill mirrors, while exact-SHA fixture testing remains unaffected.

Also redesigned the `can_approve_pull_request_reviews: false` bootstrap-PR fallback (surfaced by hosted-agent auto-review as a dead end: a plain compare-URL issue could never satisfy the bot-authorship-gated review contract) into a trusted signed-provenance-record path: the bootstrap run stamps a machine-readable provenance line (repo/run/base branch/head branch/head SHA/compare URL) into the fallback issue, and `squad-review-guard.mjs` validates a human-opened Cast PR against that record end-to-end — including bootstrap-run success — before granting the same base-controlled roles as the bot-authored path, with forged/unrelated/malformed records still failing closed.

No stable release is published by this change. Real (non-mocked) `gh aw compile --strict` against the canonical `workflows/*.md` sources continues to produce exactly the two documented warnings (`pull_request_target` advisory on `squad-review.md`, bot-trigger advisory on `squad.md`).

### Architectural correction: no credential may back the human-review continuation step, not even read-only

A second review pass on the `resume-fallback` job design above rejected it outright: **no PAT, GitHub App token, or repository/environment secret may ever be used to observe or validate the manually opened Cast PR, even read-only** — a workflow-held credential capable of reading that PR's state undermines the `can_approve_pull_request_reviews=false` trust boundary, which exists specifically so a human must do this step outside of any credential CI controls.

**Fix**: the `resume-fallback` Actions job, its `squad-gh-aw-hosted-e2e-resume` dispatch trigger, and the second `repository_dispatch` event type were removed entirely from `.github/workflows/squad-gh-aw-hosted-e2e.yml` (it is now byte-identical to its pre-`resume-fallback` baseline — no job, no secret, no action-gating). `hosted()`'s `fallback` branch no longer calls `bootstrapOutputs()`/`selectManualFallbackCastPr()`/`waitForBaseControlledReviewCanary()` inline or makes any further GitHub API call at all: it now parses the fallback issue's *own already-fetched* provenance body (via the existing pure function `parseBootstrapPrFallbackProvenance`) to terminate immediately and non-terminally at `status: 'awaiting_manual_pr'`, writing complete evidence (exact target, fallback issue URL, head/base branch/SHA, compare URL, and a `next_step` instruction) with zero additional network calls. The target repository's own installed Squad Review workflow — using that repository's own `GITHUB_TOKEN`/gh-aw authority, not ours — validates the human-opened PR locally; no cross-repository read by the hosted-E2E controller is needed for that.

`resumeFallback()` is retained, unchanged in its internal (GET-only, proven by transitive call-graph test) logic, but is now framed exclusively as a **local, operator-run-only CLI command**: never wired to any Actions job or `repository_dispatch` trigger, and relying only on whatever `gh auth login` session the operator has configured on their own workstation (never a repository secret). An operator who wants to check on a prior `awaiting_manual_pr` run downloads that run's evidence artifact themselves (`gh run download ... --name squad-gh-aw-hosted-e2e-<run-id>`) and runs `node scripts/gh-aw-hosted-e2e.mjs resume-fallback` locally, authenticated as themselves.

Added/updated regression coverage: the workflow-topology test now asserts a single `hosted-e2e` job/single dispatch type and the explicit absence of any `resume-fallback` job; a new test asserts `hosted()`'s fallback branch writes complete evidence with none of the removed function calls present in its source; the dispatcher-wiring test now also asserts `resumeFallback`'s doc comment explicitly states it is operator-run-only, never CI-wired, and never backed by a repository secret, and that the workflow file contains no reference to it at all. The existing transitive read-only call-graph proof for `resumeFallback()` and its reachable functions is unchanged and still passes.

### Follow-up: fresh Copilot review on commit `bb805b2c` (2 new findings, 3 previously missed in code unchanged since last review)

- **`squad-bootstrap-validator.mjs`, `findExistingBootstrapPrFallbackIssue` — Medium: "Avoid ambiguous matches from stale fallback records"**: a genuine regression introduced by this session's own prior fix above (making `baseSha` optional for the review-path caller). Root cause: the push-triggered rerun always supplies its own live `baseSha` for dedupe; when the default branch advances between reruns, the old record's `base_sha` no longer matches, so the push path files a *fresh* fallback issue without ever closing the *old*, now-stale one. The review-path caller (which intentionally omits `baseSha`, matching only on `repository`/`baseBranch`/`headSha`) then saw both the stale and fresh issue as valid matches and threw "Ambiguous" even though exactly one was actually recoverable — permanently stalling manual recovery the moment base drift plus a stale leftover issue coincided. **Fix**: when `baseSha` is omitted, matches are no longer unconditionally treated as ambiguous. They are deterministically resolved to the single most-recently-created match — but *only* when the coexisting matches disagree on their recorded `base_sha` (the one shape base-drift succession actually produces); multiple matches that share the *identical* `base_sha` (a genuine, unexplained duplicate — e.g. a racing concurrent rerun) still fail closed with the original ambiguity error, regardless of whether the caller supplied `baseSha`.
